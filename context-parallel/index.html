Context Parallel
长序列如何在多卡上协作

把同一条序列的 token 分给多张 GPU。每张卡只更新自己负责的 token，却仍通过通信，保留完整的注意力关系。

01 / 输入分片

一条样本已经放不下，怎么继续分？

数据并行（DP）把不同样本分给不同 GPU。但如果一篇超长文档本身就占满了单卡显存，即使每张卡只放一条样本也无济于事。Context Parallel（CP）沿这条样本的序列长度维度继续切分，让一组 GPU 合作处理同一条序列。

X: [B, S, D] → Xr: [B, S/P, D]

B 是 batch size，S 是 token 数，D 是隐藏维度，P 是 CP 并行度。忽略其他并行方式时，每张卡只保存、更新自己负责的 token 的隐藏状态，中间激活也随之分散。

比如将一条 8-token 序列连续分给 4 张卡，每张卡负责 2 个位置。它们仍然属于同一条样本，模型权重在逻辑上也属于同一个模型。

02 / 交互观察

每张卡负责一些行，但这些行仍需要跨卡的列

行是 query 的位置，列是 key/value 的位置。选择 GPU，查看它需要完成的 Q/K 配对；再切换首尾配对，观察同样的 token 数如何对应不同计算量。G0–G3 表示 K/V 原来属于哪张 GPU。

GPU3 · Q 位置 7, 8 · 有效 QK 对 15
K/V 位置 →
●所选卡计算 其他卡计算 ×未来位置被遮罩

本地 Q × 全局可见 K/V。分片决定谁来计算某个 query 的输出；mask 决定这个 query 能看哪些 key。CP 本身不截断上下文。

对单个 attention head，本卡计算的是：

Or = softmax(QrKT / √d + Mr)V

其中 Qr 是本卡的 query，K、V 逻辑上覆盖全序列，Mr 是对应这些 query 的 mask。对于因果注意力，未来位置仍被屏蔽。“全局可见”不代表一次把完整 K/V 全部留在显存里。

03 / 前向通信

Q 留在原地，K/V 分块传过来

在 pass-KV 的环形实现中，每张卡先用本地 Q 和本地 K/V 计算，然后把 K/V 传给下一张卡，接收上一张卡的块。Q 始终留在本卡。下表按 GPU0 → GPU1 → GPU2 → GPU3 → GPU0 的方向轮转。

每一轮，各 GPU 的本地 Q 正在配哪个 K/V 块
轮次GPU0GPU1GPU2GPU3
本地计算KV₀KV₁KV₂KV₃
交换 1 次KV₃KV₀KV₁KV₂
交换 2 次KV₂KV₃KV₀KV₁
交换 3 次KV₁KV₂KV₃KV₀

KVᵣ 表示最初放在 GPU r 上的 K/V 块。表格展示块的传递顺序；实际 causal kernel 会屏蔽未来位置，并可跳过完全无效的计算。它不会让早期 query 看到未来 token。

理想情况下，当前块的计算与下一块的传输重叠。Ring Attention 的价值不仅是分块，还在于尽可能减少等待通信的时间。

文章里的 allgather 和 alltoall

PyTorch 的 pass-KV 路径中，allgather 一次收集各卡 K/V，再按块计算；收集过程可以与本地块计算部分重叠。alltoall 则用于环形交换 K/V，通常需要多轮通信。

这里的 alltoall 不等于 Ulysses 的完整算法。Ulysses 通常将“部分序列、全部 heads”的布局转成“完整序列、部分 heads”，算完 attention 再转回来。相同的通信原语可以服务于不同的数据布局。

04 / 精确合并

分块计算，仍然属于同一个 softmax

每个 K/V 块的 attention 输出不能直接相加，也不能简单平均。对同一个 query，softmax 的分母必须覆盖所有允许访问的 key。

记 sj 为经过缩放和 mask 处理后的注意力分数，第 b 块的分母和局部输出为：

Zb = Σj∈b exp(sj)
ob = Σj∈b exp(sj)vj / Zb

完整输出要按分母加权：

o = Σb Zbob / Σb Zb

举例：两个块各一个 key，分数是 0 和 ln 3，value 是 0 和 10。局部输出分别为 0 和 10，但全局权重是 ¼ 和 ¾，正确输出是 7.5；直接平均得到的 5 是错误的。

实际实现用 running max、logsumexp 等统计量稳定地增量合并，不会直接计算可能溢出的指数。完全被 mask 的块贡献为零。数学上仍是原 attention，浮点运算顺序变化可能带来微小差异。

05 / Transformer 层

Attention 前后的计算，大多仍可按 token 本地完成

  1. 本地归一化。RMSNorm / LayerNorm 通常沿每个 token 的隐藏维度计算。
  2. 生成 Q/K/V。本地 Xr 乘投影权重，得到 Qr、Kr、Vr；位置编码保留全局位置。
  3. 跨卡 attention。本地 Q 配合交换来的 K/V，正确合并所有有效块的贡献。
  4. 本地输出投影、残差、MLP。对标准稠密 Transformer，这些操作不要求混合不同 token 的隐藏状态。
  5. 输出继续分片。X′r 直接进入下一层，到了下一层 attention 再交换所需信息。

不必每层都把整条序列重新聚合。各卡得到的是自己负责的位置、已经融合了全局可见上下文的输出。

这里先忽略 TP、FSDP、MoE 等其他并行产生的通信。训练时输入 token 都已知，因此可在 causal mask 下同时计算；推理时逐步生成尚未知晓的新 token，是另一种执行场景。

06 / 反向传播

K/V 被多张卡使用，梯度也要汇总

前向中，一个 K/V 块会影响多张卡的 query 输出，因此反向不能让每张卡独立结束。

  • dQ：同一份本地 Q 与不同 K/V 块交互产生的贡献，在本地累加。
  • dK / dV：累加来自不同 query 分片的贡献，并返回 K/V 所属的 rank。
  • 模型参数梯度：各 token 对共享权重的贡献需要跨 CP 组正确归约。
  • loss：按所有有效 token 的约定计算和归一化；若各卡有效 token 数不同，不能直接平均各卡的局部平均 loss。

输入和标签也必须一致分片。对于 next-token 训练，应保留原序列中的标签对应关系，不能在每个局部片段内单独移位而丢掉分片边界上的预测目标。

07 / 正确性与负载

位置不能重置，mask 不能丢掉跨卡上下文

保留 token 原来的位置编号

交互演示用 1–8 方便阅读；代码一般从 0 开始编号。原位置为 4、5 的 token 分到某张卡后，positions 仍然是 4、5，不能重新变成 0、1。否则跨卡 Q/K 的 RoPE 位置关系就变了。

全局 positions:  [0, 1, 2, 3, 4, 5, 6, 7]
本卡选择的索引:  [4, 5]
本卡 positions:  [4, 5]  // 随 token 一起切分

原文代码先生成全局 positions，再和 inputs、labels 一起切分，这个思路正确。“切分后重算”应理解为确保分片与全局位置对应，不能理解为每卡重新从零编号。

为什么 mask 只切 Q 维？

逻辑上的 mask 是 [B,H,Q,KV]。本卡只计算部分 Q，所以只取对应行；这些行仍可能访问其他卡的 key，因此 KV 维要保持全局可见关系。原文“query 只需要本段 KV”的表述不准确。

全局可见关系不等于必须分配一张完整稠密 mask；BlockMask 等表示可以紧凑地描述它。

headtail 如何均衡负载？

因果注意力越靠后，能看到的 key 越多。连续分片容易让前面的卡空闲、后面的卡繁忙。headtail 把序列切成 2P 块，将第 r 块与第 2P−1−r 块配给 rank r。

这样把前段较少的计算和后段较多的计算配对。它只改变 token 归哪张 GPU，保持全局顺序和 mask 语义。FlexAttention 的稀疏 mask 也可以采用基于实际块工作量的负载均衡方案。

08 / 对照源码

TorchTitan 把数据分片与 attention 协作接起来

对应原文所讨论版本的三个接入点
入口职责
prepare_context_parallel_input
cp_shard		输入、标签、位置一致分片；处理 mask 和负载均衡。
apply_cp_to_attention_module将 attention 包装模块接入 CP 感知的执行计划。
create_context_parallel_ctx在相应调用路径中管理 buffer 分片、恢复和 CP 执行上下文。

SDPA 是函数，把它放进 nn.Module 包装器后，框架才能按模块挂接并行计划。底层分布式 attention 负责 K/V 通信、计算调度和结果合并。

CP 必须配 FSDP 吗？

算法上不必须。CP 切序列相关激活，FSDP 切参数、梯度和优化器状态。CP 可以与复制的权重一起工作，前提是正确同步共享权重梯度。

原文所讨论的 TorchTitan 方案将 dp_shard 与 cp 合并进 FSDP 网格，让参数 all-gather 与梯度 reduce-scatter 一并覆盖这些 GPU。这是工程设计选择，不是 CP 的数学前提。

09 / 资源开销

每卡负担下降，总稠密 attention 计算量仍在

举例，B=1、S=131072（128K）、D=8192、BF16 时，一份 [B,S,D] 隐藏状态就占 2 GiB。CP=8 均匀分片后，每卡这份张量约 256 MiB。训练中的多份中间激活会一同受益。

但整个训练峰值显存不能保证直接除以 P。参数、通信缓冲区、临时工作区，以及 all-gather 路径下收集的完整 K/V，都可能不按这个比例缩小。

总 attention: O(S²d)
每卡 attention: O((S/P) × S × d) = O(S²d/P)

这里按单个 head 计量，并忽略 causal 带来的常数因子。每卡只有 S/P 个 query，但每个 query 仍处理全局可见的 key，不能漏掉跨分片计算而误写成 O((S/P)²d)。

FlashAttention 避免将完整 S×S 分数矩阵写入显存；CP 则进一步把长序列激活与计算分散到多卡。两者可以组合。训练中的显存问题也不应只用推理场景里的“KV cache”来解释。

序列固定时，CP 度越大，本地块越小，通信延迟和同步就越难隐藏。真正的提速取决于序列长度、GPU 互联、注意力后端、负载均衡与其他并行方式。

10 / 并行方式

它们分配的是不同的维度

方式主要分配什么
DP / 数据并行不同样本。
CP / 上下文并行同一样本中的不同 token 位置及相关激活。
TP / 张量并行层内矩阵计算的不同部分，如隐藏维度或 heads。
PP / 流水线并行不同 Transformer 层。
FSDP参数、梯度与优化器状态的存储分片。

Megatron 中狭义的 Sequence Parallel（SP），主要配合 TP 切分 LayerNorm、Dropout 等区域的激活；CP 则让序列分片贯穿模型，并处理 attention 的跨分片依赖。论文里的 sequence parallelism 有时是更广义的总称，阅读时要先确认定义。
